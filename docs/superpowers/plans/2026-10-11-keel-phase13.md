# Keel Phase 13 Implementation Plan: text inside documents in library search

> **For agentic workers:** same rules as earlier plan headers. Read [docs/parity.md](../../parity.md) first (ranked gap #11). The task gets its own worktree, branched from the release Phase 13 starts on (0.21.0). Run `cargo fmt --all --check`, `cargo clippy --all-targets -- -D warnings` and the tests of the crates touched before every commit. Any new parser of outside bytes gets a fuzz target (see [docs/fuzzing.md](../../fuzzing.md)); the text extractors already have one through the preview target. Every user-visible change goes into the docs and the CHANGELOG in the same task. Public repo: no hostnames, IPs, user names, personal names or personal paths in code, tests, fixtures, screenshots or commit messages.

**Goal:** Library search finds words inside documents, not only in names: the text of plain, code, Markdown, PDF, Word, spreadsheet, presentation and OpenDocument files is extracted by an idle job into each source store and searched with FTS5, with a snippet in the results. Spec section 2.10 (search) and parity gap #11. OCR of images and scanned PDFs stays out (noted as the follow-up).

**Live checks.** On the owner's Windows desktop with generated fixtures in a temporary folder and `KEEL_CONFIG_DIR`, `KEEL_DATA_DIR` and `KEEL_NET_SECRET=memory` set as the first statement of every shell command, so the owner's settings, library and keyring are never touched.

**Review focus:**
1. Extraction never runs outside the size and time caps, never on remote or cloud sources unless the setting says so, and a damaged file is "skipped", never a crash report.
2. The text table and its FTS index never make the store unusable on an older Keel beyond the documented "newer than this Keel" refusal, and a backup strips and rebuilds them like the name index.
3. A content query is bounded: results capped, snippets bounded, the FTS query built from the user's words with the MATCH syntax escaped (a user cannot write FTS5 operators that error or scan everything).
4. The job is idle-priority, resumable, pauses on battery and user activity like the sidecar job, and never holds a store write lock across an extraction.
5. Privacy: extracted text stays inside the store on disk, never in logs, crash reports, sync pages or the daemon's HTTP responses beyond the snippet asked for.

### Task 62: text inside documents (worktree `task62`)

**Read:**
- `crates/keel-core/src/sidecar_job.rs` and `sidecars.rs` (the idle job pattern: checkpoints, resume, battery and activity pauses, per-record keys by mtime+size+content id), `hash.rs` (`background_thread`), `jobs.rs`.
- `crates/keel-core/src/schema.sql` (`record_fts`, the `@source` steps; the next step is 12), `search.rs` (`LibraryQuery::parse`, how `record_fts` is queried, `KindFilter`), `backup.rs` (what is stripped and rebuilt), `library.rs` (`stats`).
- `crates/keel-preview/src/{text,pdf,docx,office,pptx,odf,table}.rs` and `lib.rs` (`Preview::Text`, the readers' size caps, `init_pdfium`); `docs/fuzzing.md`.
- `crates/keel-app/src/search_tab.rs`, `chip_row.rs`, `crates/keel-core/src/chips.rs`, `crates/keel-web` (the search page), `crates/keel-api/src/ops.rs` (`search`, `library.stats`), `docs/library.md` (Searching), `docs/api.md`.

**Design points:**
- **Extraction** lives in `keel-preview` as one function, `extract_text(path, ext, cap) -> Result<Extracted>` (text, plus `truncated: bool`), reusing the readers the preview already has: plain text and code (with the existing encoding detection), Markdown, PDF through pdfium (text only, first N pages until the cap), docx, xlsx/xls/xlsb/ods (cell text, sheet by sheet), pptx/odp (slide text), odt. Caps: 8 MiB input (PDF 64 MiB), 200,000 characters of output, 10 s per file (pdfium on a worker with the existing kill), after which the record is marked truncated. Formats without a reader are skipped, not failed.
- **Storage:** `-- @source 12`: a `record_text(record INTEGER PRIMARY KEY, mtime INTEGER, size INTEGER, chars INTEGER, truncated INTEGER, status INTEGER)` row per attempted record (status: done / skipped-kind / skipped-size / failed) and an external-content FTS5 table `record_content USING fts5(text, content='', tokenize='unicode61 remove_diacritics 2')` keyed by record id (contentless: the text is not stored twice; the snippet comes from `snippet()` on the FTS row, which needs the text in the index, so use a regular content table `record_text_body(record, text)` if contentless cannot give snippets; say which). Delete triggers mirror `record_fts`'s. The backup strips `record_content`/`record_text_body` like the name index and the restore queues the job again.
- **The job** (`text_job.rs`): per source, idle priority, same pauses and checkpoints as the sidecar job; a record is (re)extracted when its mtime or size changed; failures counted, the first 20 logged. Runs where the library runs (the daemon when attached). Started by the walk and by F5 like sidecars; `keel sources index` triggers it; a `library.text` stat (records done, skipped, failed, chars) in `library.stats`.
- **Setting:** **Index file contents** in Settings → Library: on by default for local sources; off for SFTP, cloud and `node://` sources unless the per-source switch is turned on (a remote read of every document is a real cost: say so in the setting's hint). A per-source switch in the source's row.
- **Query:** bare words match names and contents by default once the index has rows (a result from content shows a snippet line under the name, with the matched words emphasized); `content:word` and `name:word` restrict to one; `-content:` excludes. The FTS query is built from the parsed words with each word quoted (`"word"*` for prefix) so user text never reaches FTS5 operators; a phrase in quotes becomes an FTS phrase. Results stay capped as today; snippets are at most 160 characters, one per result, computed only for the page shown.
- **Chips:** a **Contents** chip (on: search contents; off: names only), with the term it adds shown on hover, in the desktop row and the web client's.
- **API and web:** `search` gains `contents: bool` (default true) and each hit an optional `snippet`; the web client's search page shows the snippet and the chip. The daemon's HTTP never returns more than the snippet.
- **OCR:** not in this phase; `docs/library.md` says images and scanned PDFs are not searched by content yet.

**Tests:**
- Extraction: one fixture per format under `crates/keel-preview/fixtures/` (tiny, synthetic, generated by a test helper or committed at under 20 KB each; "Keel / Test Document" wording, no personal data), the caps (a 9 MiB text file skipped-size, a 250,000-character file truncated), a damaged docx and a damaged PDF skipped with status failed, an unknown extension skipped-kind.
- Store: the migration from 11 to 12 on a fresh and an existing store; delete triggers; the backup strips and the restore rebuilds (the backup test gains a text row).
- Job: a source with 30 files of mixed kinds indexes all, re-extracts a changed file, checkpoints and resumes (the sidecar job's resume test pattern), pauses for activity.
- Query: words match content, `content:`/`name:` restrict, a phrase, prefix, an FTS operator typed by the user (`NEAR(`, `"` unbalanced, `*`, `OR`) never errors; snippets bounded; a source with contents off is not matched by content.
- Walkthrough flow: index a fixture folder, search a word that is only inside a document, the hit shows with its snippet, the Contents chip off hides it.
- **Live (desktop):** a fixture folder with 200 generated documents of every format; the job finishes under a minute; three searches by content in the window and one through `keel search --json` show snippets; `library.stats` reports the text counts.
