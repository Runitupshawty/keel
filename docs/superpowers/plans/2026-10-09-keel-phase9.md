# Keel Phase 9 Implementation Plan: web client, phones, mounts (stretch)

> **For agentic workers:** same rules as earlier plan headers. Read spec 2.10 ("Clients", "Mounts"), the Phase 8 plan (keel-daemon JSON-RPC + WebSocket, keel-api operation registry, keel-net devices/Spacedrop), and `docs/api.md` (written by Task 37). Everything here is a client of the daemon's API: no new core logic, no second implementation of operations. Phase 9 ships only after Phase 8 is released.

**Goal:** James can open his library from any browser and from his phone: browse sources (including offline ones from the index), search, preview, tag, run previewed operations, and send or receive Spacedrops, all through `keel-daemon` on a machine he owns (reachable on the LAN or over his tailnet). Mounts expose a source or subtree as a drive letter or mount point.

**Security rules:** the web client only ever talks to the daemon's WebSocket with the bearer token (never a file path or local socket); the daemon serves the client's static files itself so there is no third-party host; TLS is the tailnet's or a reverse proxy's job (documented), the daemon refuses non-loopback binds without `--ws-allow-remote` as in Phase 8; the token is entered once per browser and kept in `localStorage` only when the user ticks "remember on this device"; previews work exactly as in the desktop app (validate → preview → execute, with the same warnings); no analytics, no CDN, no external fonts.

**Review focus:** (1) a token leak through URL, referrer, logs or the browser history is impossible; (2) a previewed plan cannot be executed with different input from a second tab; (3) the client never shows an operation as done before the daemon's job finished; (4) the phone share-sheet path (PWA share target) never uploads to anything but the chosen device; (5) mounts never hand a partially written file to another program.

---

### Task 39: `keel-web` browser client (worktree `task39`)
- Crate `crates/keel-web`: the existing egui UI compiled to `wasm32-unknown-unknown` with `eframe`'s web backend is the first choice (same look, same keymap, one codebase); the local-only parts (terminal, drag-out, single instance, hotkey, Everything/NTFS search, archive mounting through local files) are behind `cfg(not(target_arch = "wasm32"))`; the `Router` gets a `DaemonProvider` that answers every VFS call (`list`, `stat`, `read` ranges, `write`, mkdir/rename/remove via plan+execute) over the WebSocket JSON-RPC, and the library, search, tags, jobs and devices panels call the `keel-api` operations directly. If the wasm build of keel-app proves impractical within the task (crate incompatibilities), fall back to a small purpose-built egui web app in `keel-web` that reuses the view modules it can.
- The daemon serves the client: `keel-daemon --web` (off by default) serves `/` from the embedded wasm bundle (`include_dir`) and `/rpc` as the WebSocket; the first visit asks for the token; "remember on this device" stores it in `localStorage`; the client reconnects with backoff and shows connection state.
- Previews and thumbnails come from the daemon (`preview.render` and `media.thumb` operations added to keel-api, bounded sizes, cached by content id); streaming downloads through `/file/<plan token>` links that expire after use.
- Tests: wasm build in CI (`wasm32-unknown-unknown` target, `wasm-bindgen-test` for the provider against a mocked daemon), a daemon integration test serving the bundle and answering `version` over the WebSocket, a token-in-URL guard test (the client refuses to read a token from the query string).
- Commit `feat(web): browser client served by keel-daemon`.

### Task 40: phones (worktree `task40`)
- The web client as an installable PWA: manifest, service worker (shell cached, data never cached), a phone layout (single pane, bottom bar: Browse, Search, Library, Devices; the preview panel as a full-screen sheet; long-press context menus; pull to refresh), touch gestures in the media grid and viewer (pinch zoom, swipe between items).
- Spacedrop from the phone: Web Share Target (`share_target` in the manifest) so "Share → Keel" on Android/iOS (iOS: via the installed PWA) opens the client with the shared files, lets you pick a device, and uploads through the daemon's `spacedrop.send` operation (the daemon forwards to the peer); incoming Spacedrops on the daemon's machine show in the client's inbox with a download link.
- Reaching the daemon from the phone: documented setups (same LAN; the tailnet with the daemon bound to the tailnet IP and `--ws-allow-remote`; a reverse proxy with TLS). The client warns when the connection is not TLS and not loopback.
- Tests: manifest and service-worker presence tests; a Playwright run (in CI, Chromium only) that installs the PWA shell, opens a source, searches, previews a file and previews a delete, against a daemon with a fixture library.
- Commit `feat(web): PWA, phone layout, share-sheet Spacedrop`.

### Task 41: mounts (worktree `task41`, stretch)
- `keel-mount`: expose a source or subtree as a drive letter (WinFsp via `winfsp` crate), macFUSE or FUSE (`fuser`), served from the daemon: directory listings from the index when offline, on-demand range reads through the VFS, writes staged to `.keel-partial` and published on close (so another program never sees a half-written file), an explicit "Mount…" action in the sidebar and `keel mount <source> <letter|path>` on the CLI; unmount on daemon stop.
- Tests: a FUSE/WinFsp round trip behind a feature flag and an env var (the CI runners lack the drivers; the test is `#[ignore]` and documented), a unit test of the staged-write state machine.
- Commit `feat(mount): sources as drives (WinFsp / macFUSE / FUSE)`.
