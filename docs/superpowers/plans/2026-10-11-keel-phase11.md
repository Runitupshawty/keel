# Keel Phase 11 Implementation Plan: the next parity gaps (FTP, fast small-file copies, WSL, a file finder, library backup)

> **For agentic workers:** same rules as earlier plan headers. Read [docs/parity.md](../../parity.md) first: it ranks these gaps (#6, #7, #8, #12 and #14) and says why they come next. Each task gets its own worktree, branched from the release Phase 11 starts on (0.19.0). Run `cargo fmt --all --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test --workspace` before every commit. Any new parser of outside bytes gets a fuzz target (see [docs/fuzzing.md](../../fuzzing.md)). Every user-visible change goes into the docs and the CHANGELOG in the same task. Public repo: no hostnames, IPs, user names, personal names or personal paths in code, tests, fixtures, screenshots or commit messages.

**Goal:** Close the five small gaps that [docs/parity.md](../../parity.md#ranked-gaps) ranks next: FTP and FTPS remotes (spec section 1 asks for "cloud and FTP mounts"), copying many small files several times faster, WSL distributions in the sidebar with `keel` working from inside WSL (spec section 1: CLI and WSL), a fuzzy finder over files and not only folders, and a backup and restore of the library.

**Not in this phase:** folder sync (#13) and text inside documents (#11) are each a phase of their own. Mounts in the release builds (#9) and signed builds (#10) need the owner.

**Live checks.** Wherever a brief says "live", run it on the owner's own Windows desktop, and on a Linux machine of the owner's where noted. Use only generated fixtures in a temporary folder (`%TEMP%\keel-p11-<task>` or `$TMPDIR/keel-p11-<task>`), with `KEEL_CONFIG_DIR` and `KEEL_DATA_DIR` pointed at a throwaway folder and `KEEL_NET_SECRET=memory`, so the owner's settings, library and keyring are never touched. Live coordinates (a test server's address, a user name, a password) come from environment variables that are never written into the repository.

**Review focus:**
1. Plain FTP sends passwords and files in clear text: Keel says so where the remote is added, and never silently falls back from FTPS to FTP.
2. The parallel copy keeps every guarantee of the serial one: no half files on cancel or error, the same conflict handling, a journal and an undo record that list exactly the files that landed.
3. Paths from WSL (`\\wsl.localhost\<distro>\...`) go through the same local provider rules as other UNC shares: no Recycle Bin, so deletes are permanent and say so; no watcher or search index, so the view and search fall back cleanly.
4. The file finder never stalls the window: the walk, the library read and the matching run on workers, with caps that are documented.
5. A restored backup never overwrites a library, and a crafted backup archive cannot write outside the library folder, fill the disk or crash Keel.

### Task 49: FTP and FTPS remotes (worktree `task49`)

**Goal:** A remote can be an FTP or FTPS server (NAS boxes, web hosts, cameras, old file servers), added, browsed, copied to and from, like an SFTP remote. Spec section 1 asks for "cloud and FTP mounts"; parity gap #6.

**Read:**
- `crates/keel-vfs/src/sftp/` (`mod.rs`, `conn.rs`, `auth.rs`, `hostkeys.rs`): the pattern for a synchronous remote provider, its connection pool, credential storage and trust prompts. Reuse `RemoteHost`, `RemoteAuth` and the auth store; do not copy them.
- `crates/keel-vfs/src/router.rs` (`provider_for`, `register_remote`), and every place that tests `"sftp"` outside that folder (`crates/keel-app/src/remotes.rs`, `sidebar_remotes.rs`, `state.rs`, `crates/keel-core/src/protect.rs`, `crates/keel-vfs/src/ops.rs`): each one needs a decision for FTP.
- `crates/keel-vfs/src/cloud/upload.rs` (resumable uploads) and the copy resume in `ops.rs` (`transfer_resumable`), for how an interrupted transfer continues.
- `docs/remotes.md`, `docs/features.md`, `deny.toml` (the license allow list) and `docs/fuzzing.md`.

**Design points:**
- **Protocol on the host.** `RemoteHost` gets a `protocol` field (`Sftp`, `Ftp`, `Ftps`) with a serde default of `Sftp`, so saved remotes from earlier versions load unchanged. FTP remotes use the `ftp` VPath scheme (`ftp://<host id>/<path>`), resolved by host id in the router as SFTP is.
- **Client library.** Use `suppaftp` with its `rustls` feature for FTPS (explicit TLS, `AUTH TLS` on port 21 by default; implicit TLS on port 990 when the user picks it). No OpenSSL, no new TLS stack: check `cargo deny check --offline` passes with the license allow list before anything else. If `suppaftp` cannot be made to fit (a license, a dependency `deny` refuses, or a blocking-mode gap), write the small client Keel needs (USER/PASS, PWD, CWD, TYPE I, PASV/EPSV, MLSD with LIST as a fallback, RETR, STOR, APPE, REST, SIZE, MDTM, DELE, RMD, MKD, RNFR/RNTO, QUIT) on `std::net::TcpStream` plus `rustls` for FTPS; say which in the commit.
- **Passive mode only.** Timeouts on connect, control and data (reuse the SFTP values). One control connection per provider with a pool like `ConnPool`; each transfer opens its own data connection.
- **Listings.** Prefer `MLSD` (machine-readable); fall back to `LIST` and parse the UNIX and the DOS (IIS) formats. The `LIST` line parser and the `MLSD` fact parser are parsers of outside bytes: a fuzz target each, with bounds on line length and entry count.
- **Transfers.** Downloads support `read_range` through `REST`; uploads go to a staging name and are renamed into place on finish, like SFTP uploads; an interrupted upload resumes with `APPE`/`REST` when the server reports `SIZE` of the staging file, else starts over. No trash: `remove_kind` is permanent, and the delete dialog says so, as for SFTP.
- **Security.**
  - Plain FTP: the Add remote dialog shows, next to the protocol choice, "FTP sends the password and the files unencrypted. Prefer FTPS or SFTP." and the remote's sidebar tooltip repeats it.
  - FTPS: the certificate is verified against the system roots (`rustls-platform-verifier` if it is already in the tree, else `webpki-roots`); a certificate that fails verification gets the same kind of prompt as an unknown SSH host key, showing the SHA-256 fingerprint, and the accepted fingerprint is pinned per host in the same store as known hosts. Never fall back from FTPS to FTP, and never continue a failed TLS handshake.
  - Anonymous login is allowed (user `anonymous`, an email-shaped password).
  - Passwords go to the same credential store as SFTP passwords (`KEEL_NET_SECRET=memory` in tests).
- **Where FTP is refused:** mounts of FTP remotes, hashing and library sources on FTP are out of scope: those code paths refuse with "not supported for FTP remotes" and the docs say so. `protect.rs` treats FTP like SFTP (a remote: no protection of copies there).
- **API and daemon:** whatever `keel-api` exposes for SFTP remotes (list, add, remove) gains the protocol field; `docs/api.md` shows an FTP example. The web client's Remotes page shows the protocol.

**Tests:**
- A small FTP server for tests, in `crates/keel-vfs/src/ftp/test_server.rs` under `cfg(test)`: passive mode, the commands listed above, UNIX `LIST` output, optional `MLSD`, serving a temporary folder. (A third-party test server crate is fine instead if it is small, passes `deny`, and does not pull tokio into the test build of `keel-vfs`.)
- Provider tests against it: list, stat, read, read_range, write and rename into place, resume of an interrupted upload, mkdir, remove, rename, a listing with spaces and non-ASCII names, a `LIST`-only server, a server that closes the data connection early (an error, not a hang), and cancel during a transfer.
- Unit tests of both listing parsers; the fuzz targets run for a minute each.
- An ignored live test that reads `KEEL_FTP_TEST` (`user@host:port`) and `KEEL_FTP_TEST_PASS` and does list, upload, download and delete in a folder it creates and removes.
- A walkthrough flow: Add remote with protocol FTP shows the clear-text warning; the Remotes section shows the protocol.
- **Live (the owner's Linux machine):** start a throwaway FTP server in a container with passive ports (for example `fauria/vsftpd` with `PASV_ADDRESS`, `PASV_MIN_PORT` and `PASV_MAX_PORT` set and the ports published), with a random password; run the live test and the GUI against it from the Windows desktop; remove the container after. Nothing about the machine goes into the repository.

**Docs:**
- `docs/remotes.md`: a section "FTP and FTPS" (how to add, passive mode, what is not supported, the clear-text warning, certificate pinning).
- `docs/features.md`, `docs/api.md`, `docs/fuzzing.md` (the two new targets), `docs/parity.md` (row 6 done).
- CHANGELOG: Added, Security (FTPS verification and pinning; plain FTP warning), Known limitations (no mounts, no library sources on FTP; passive mode only).

**Commits:**

- `feat(app): add and browse FTP remotes`
- `test(fuzz): FTP listing parsers`

### Task 50: copying many small files in parallel (worktree `task50`)

**Goal:** Copying thousands of small files runs several times faster. Today a plan copy of 3,000 one-byte files takes about 3.5 s (about 860 files a second, `docs/performance.md`); Atlas claims 3,800 a second. Parity gap #7.

**Read:**
- `crates/keel-vfs/src/ops.rs`: `transfer_local`, `transfer_with`, `copy_file`, `copy_resumable`, `place`, `Partial`, `Journal`, `Landed`, `plan_size`, and the per-OS `sys::copy_file` in `ops_windows.rs` and `ops_unix.rs`.
- `crates/keel-core/src/plan_tests.rs` (`three_thousand_items_copy_fast`) and `perf_tests.rs`; `scripts/perf.sh`; `docs/performance.md`.
- `crates/keel-app/src/undo.rs` (what it reads from `Landed`) and `jobs.rs` (progress and cancel).

**Design points:**
- **Measure first.** Run the copy benchmark three times in a release build before changing anything, and record the numbers; then profile one run (where does the time go: creating the file, the rename into place, metadata, progress callbacks?). Fix the cheap things first: for example, one progress callback per file instead of per chunk for small files, and skipping the second `metadata` when the copy reported its length.
- **Then parallelize.** A bounded pool of workers (default `min(8, available_parallelism)`, override with `KEEL_COPY_THREADS` for measurement) takes files under a size threshold (1 MiB to start; tune by measurement) from a queue, while files over the threshold stream one at a time so a big file keeps its single sequential stream. Folders are created in a sequential pre-pass, deepest last, before any file is queued.
- **Keep every guarantee.** Each worker still copies to a `.partial` staging name and renames into place through `place`, so cancel or an error never leaves a half file. The first error stops the queue, lets in-flight files finish or clean up, and is reported as today. `Journal` records and `Landed` entries are appended under a mutex, in the order files land. Progress is aggregated with atomics and reported at most every 50 ms. Conflicts are decided in the preflight as now.
- **Same-volume moves** stay a rename and are not touched. Resumable (journaled) transfers of big files stay sequential.
- **Target:** at least 2,500 files a second on the 3,000-file benchmark on an NVMe disk in a release build; if the machine shows the serial version is limited by something else (the rename, antivirus), say so with numbers and keep the best variant.

**Tests:**
- Every existing copy, move and undo test passes unchanged.
- New: a copy of 2,000 small files and 3 files of 8 MiB, cancelled part way, leaves no `.partial` file and reports the files that landed; a locked (Windows) or unreadable (Unix) file in the middle stops the job with that error and a consistent `Landed` list; the undo of a parallel copy trashes exactly the copies; `KEEL_COPY_THREADS=1` gives the same results.
- The benchmark budget in `three_thousand_items_copy_fast` tightened to the new number with a margin.

**Docs:**
- `docs/performance.md`: the new numbers and how the pool works, with the env var.
- CHANGELOG: Changed ("Copying many small files is N times faster").

**Commits:**
- `perf(vfs): cheaper per-file work in copies` (if anything came out of the profile)
- `perf(vfs): copy small files on a worker pool`
- `docs: copy performance`

### Task 51: WSL distributions in the sidebar, and `keel` from inside WSL (worktree `task51`)

**Goal:** On Windows with WSL installed, each distribution's files appear in the sidebar and open like a share, and running `keel <path>` inside a distribution opens that folder in the Windows window. Spec section 1 (CLI and WSL); parity gap #8.

**Read:**
- `crates/keel-app/src/sidebar.rs` and `volume.rs` in `keel-vfs` (how drives are listed and refreshed).
- `crates/keel-vfs/src/local.rs` and `ops_windows.rs`: how UNC paths are handled today (long paths, `is_fixed_disk`, `trash_path` refusing what has no Recycle Bin, the watcher).
- `crates/keel-app/src/cli.rs` and `main.rs` (opening a path from the command line, single instance), `crates/keel-app/src/term_pane.rs` (it already lists WSL distributions for the terminal: reuse that listing, do not write a second one).
- `docs/files.md` (terminal and sidebar), `docs/getting-started.md`.

**Design points:**
- **Listing distributions** comes from the registry (`HKCU\Software\Microsoft\Windows\CurrentVersion\Lxss\<guid>\DistributionName`, with `DefaultDistribution`), never from `wsl.exe --list` (UTF-16 output, slow, starts the service). If the key is missing there is no WSL and the section is not shown. A "WSL" sidebar section lists the distributions, default first.
- **Opening one** navigates to `\\wsl.localhost\<name>\` (falling back to `\\wsl$\<name>\` when the first does not resolve), through the local provider as any UNC share. Opening a stopped distribution starts it (Windows does that on first access); the sidebar shows "starting" for the seconds it takes rather than freezing: the listing runs on a worker with a timeout and an error toast "Could not open <name>: ...".
- **What differs on a WSL share, said in the docs and the UI:** no Recycle Bin (deletes are permanent and the dialog says so, as on other UNC paths); the folder watcher may not report changes (refresh with F5; say so in Known limitations); Everything does not index it (search falls back to the walk); file ownership and mode bits are Linux's (Properties shows what Windows reports).
- **`keel` inside WSL.** The Linux build of `keel`, when `WSL_DISTRO_NAME` is set and it is asked to open a path (no subcommand): translate the path with a pure function (`/mnt/<x>/...` to `<X>:\...`; any other absolute path to `\\wsl.localhost\<WSL_DISTRO_NAME>\...`; a relative path is resolved against the current directory first), find `keel.exe` on the Windows `PATH` that WSL interop appends (or `KEEL_EXE` if set), run it with the translated path and exit with its code. `--here` (or `KEEL_WSL_NATIVE=1`) keeps the Linux window (WSLg). Subcommands (`search`, `du`, `mcp`, ...) keep running in the Linux process as today.
- **`keel.exe .` from WSL** also works: when the Windows binary is started with a relative path and a UNC current directory, it opens that folder. Check the single-instance hand-off accepts UNC paths.
- **Documentation for the shim:** `docs/wsl.md` explains both ways (installing the Linux tarball inside the distribution, or an alias `keel='keel.exe'`), and the install script for Linux mentions WSL.

**Tests:**
- Unit tests of the registry parsing on a value list (not the live registry), of the path translation (`/mnt/c/Users/x`, `/home/x`, `/`, a relative path, names with spaces and non-ASCII), and of the `keel.exe` lookup over a `PATH` string.
- A Windows test that opens `\\wsl.localhost\<name>\` is only possible on a machine with WSL: write it as an ignored test that reads `KEEL_WSL_TEST=<distro>`.
- A walkthrough flow with a fake distribution list: the section shows, the default is first, a stopped one opens through the navigation path (the provider call is stubbed).
- **Live:** WSL is not installed on the owner's desktop (see Needs the owner). Do everything that can be done without it, mark the feature "not yet checked on a machine with WSL" in Known limitations, and list the exact live steps in `docs/wsl.md` under "Checking", so the owner can run them.

**Docs:**
- `docs/wsl.md` (new), linked from `docs/files.md` and `docs/getting-started.md`; `docs/features.md`; `docs/parity.md` (row 8 done, with the live-check caveat).
- CHANGELOG: Added, Known limitations (watcher, no Recycle Bin, not yet live-checked).

**Commits:**
- `feat(app): WSL distributions in the sidebar`
- `feat(app): keel inside WSL opens the Windows window`
- `docs: WSL`

### Task 52: a fuzzy finder over files (worktree `task52`)

**Goal:** Ctrl+P finds files as well as folders: type a few letters of a name and jump to the file, selected and previewed in its folder. Atlas's fuzzy finder; parity gap #12.

**Read:**
- `crates/keel-app/src/jump.rs` (Ctrl+P today: the folder index from Everything `folder:` or a home walk, nucleo on its own thread, `WALK_CAP`, `REINDEX_AFTER`) and `crates/keel-search/src/fuzzy.rs`, `lib.rs` (`folder_index`, `walk`).
- `crates/keel-core/src/library.rs` and the `files.list` operation in `keel-api/src/ops.rs` (how to read names from the library index cheaply), `crates/keel-app/src/palette.rs`.
- `docs/files.md` (Ctrl+P), `docs/getting-started.md`.

**Design points:**
- **Scope of the file list.** Everything's complete file list is millions of names, too many to score per keystroke, so the finder matches files from two bounded sources: the current folder's tree (a worker walk, newest first, capped at `WALK_CAP` entries, with the cap shown as "first 50,000 files" in the popup) and the library index (names with their relative paths, capped and documented, read once per open and reused for `REINDEX_AFTER`). Folders keep their existing machine-wide index.
- **One popup, a filter.** Ctrl+P opens as today; Tab cycles Folders, Files, Both (default Both, remembered per profile); each result shows a kind icon and its folder dimmed. Enter on a file navigates to its folder, selects it and previews it; Enter on a folder navigates. Shift+Enter opens in the other pane.
- **Ranking:** nucleo scores; ties prefer shorter paths and the current folder's tree over the library.
- **Never stall the UI:** the walk and the library read run on workers; matching stays on the finder thread; results are delivered in batches; the popup shows "indexing…" with counts until the first batch.
- **Attached to the daemon:** the library names come through the API (add a `files.names` operation with a cap if `files.list` is too heavy; document it).

**Tests:**
- Unit tests of the ranking and of the cap messages.
- A walkthrough flow (kittest): in a fixture tree, Ctrl+P, type part of a file name, Enter, and the file is selected in its folder with the preview open; Tab switches to Folders and the file disappears from the results.
- A test that a tree with more than the cap reports the cap and still answers.
- **Live (Windows desktop):** a fixture folder with 20,000 generated files; Ctrl+P answers within a second per keystroke, and the window stays responsive while indexing.

**Docs:**
- `docs/files.md` (Ctrl+P section), `docs/getting-started.md`, `docs/features.md`, `docs/api.md` if an operation was added, `docs/parity.md` (row 12 done).
- CHANGELOG: Added, Known limitations (the caps).

**Commits:**
- `feat(app): Ctrl+P finds files`
- `docs: file finder`

### Task 53: library backup and restore (worktree `task53`)

**Goal:** A library that was hashed, tagged and marked with favorites is worth keeping: one command writes it to a file, and one restores it, on this or another machine. Spacedrive has it; parity gap #14.

**Read:**
- `crates/keel-core/src/library.rs` (`open`, the library folder: `library.db` and `sources/*.db`, `Pool`), `profiles.rs` in `keel-app`.
- `crates/keel-api/src/ops.rs` (`library.*` operations, the previewed-operation pattern) and `docs/api.md`.
- `crates/keel-vfs/src/archive/` (the zip reader and writer already in the tree, and their bounds).
- `docs/library.md`, `docs/daemon.md`.

**Design points:**
- **Format:** a zip named `<library>-<date>.keelbackup` holding `manifest.json` (format version, Keel version, library name, created time, the source ids and their roots and volume ids, a SHA-256 per file) and a consistent copy of each database made with `VACUUM INTO` on the live connection (no file copy of a database in use). Previews, thumbnails and the search index are not included: they are rebuilt.
- **Commands:** `keel library backup <file>` and `keel library restore <file> [--as <name>]`; API operations `library.backup` and `library.restore` (previewed: the preview lists what the file holds and what the restore would create); palette entries "Back up library…" and "Restore library…" with the native file dialogs already used elsewhere; a line in Settings > Library with the last backup time.
- **Restore never overwrites.** It creates a library under the manifest's name, or `--as <name>`; if that name exists it refuses ("a library named X exists; use --as"). Sources whose root exists on this machine come back online and are re-walked; the others show as offline, as after a drive is unplugged. Profiles are not part of the backup.
- **Reading an outside file safely:** entry names must be exactly the ones the manifest lists (no paths, no `..`), each entry is bounded in size (refuse over 4 GiB and over a ratio of 100:1), the manifest is bounded (1 MiB) and parsed with serde, the SHA-256 of each database must match the manifest, and each database is opened read-only with `PRAGMA quick_check` before it is moved into place. Anything else is "not a Keel backup" or "damaged backup", never a crash report. A fuzz target for the archive reader.
- **Attached to the daemon:** the daemon holds the databases, so both operations run in the daemon when attached and the files are written where the client asked (local paths only).

**Tests:**
- Backup then restore into a fresh data dir: file counts, tags, favorites, content ids and source list are identical; the restored library's sources resolve to the fixture roots.
- Restore refuses an existing name; `--as` works; a backup made while an index job is running is consistent (`quick_check` passes and the counts are a snapshot).
- Crafted archives: a path entry, an extra entry, an oversized entry, a wrong hash, a manifest with a newer format version (refused with "made by a newer Keel"), a truncated file.
- The CLI round trip through `keel`; the same through the API with the daemon running (the daemon tests pattern).
- **Live (Windows desktop):** a fixture library of a few hundred files with tags; back up, delete the library's folder from a throwaway data dir, restore, and check the tags are back.

**Docs:**
- `docs/library.md`: a section "Backup and restore" (what is in the file, what is not, restoring on another machine).
- `docs/api.md`, `docs/daemon.md`, `docs/features.md`, `docs/fuzzing.md`, `docs/parity.md` (row 14 done).
- CHANGELOG: Added, Known limitations (no automatic backups; thumbnails rebuilt).

**Commits:**
- `feat(core): library backup and restore`
- `feat(app): back up and restore from the palette and the CLI`
- `test(fuzz): backup archive reader`
- `docs: library backup`
